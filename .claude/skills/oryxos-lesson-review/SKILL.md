# OryxOS 节级复习 Skill

## User Input

```text
$ARGUMENTS
```

节号来自上面的输入。

## 总纪律

1. **只读不写代码**：本 skill 只读取和分析已有代码，不修改任何 Java/配置/测试文件。
2. **产出落盘**：复习文件写入 `.oryxos/review/lesson-{N}-{slug}.md`；累计总图追加到 `.oryxos/review/master-diagram.md`。
3. **停等**：生成完复习文件后停下，不做 commit / push。

## 第 2 步：生成 review 文件

输出路径：`.oryxos/review/lesson-{N}-{slug}.md`

slug 取自课件文件名，如第 16 节为 `provider`，第 17 节为 `react`。

文件结构固定如下（按顺序输出）：

### 2.1 文件头部

```markdown
# 第{N}节复习：{模块名}

> AI 写代码，你画地图。地图上只标三样东西：**入口在哪 → 经过哪 → 出口在哪**。
```

### 2.2 必读区

#### (A) 接口清单

按三级优先级排列：

```
## 必读区

### 接口清单

#### ★★★★ 接口 / 抽象类（模块的"形状"——契约）

| 文件 | 类/接口 | 角色 | 核心方法 | 入参 | 出参 |
|------|---------|------|---------|------|------|
| {path} | {Name} | {接口/抽象类/record} | {methodSig} | {入参类型} | {返回类型} |
```

- 只列本课**新增或修改**的 public 接口/抽象类/record。
- 方法签名精简到核心 1~2 个。
- 一句话解释"角色"：这个类型在模块里干什么。

#### ★★★ 核心实现（"组装逻辑"——怎么把接口和实现串起来）

```
#### ★★★ 核心实现

| 文件 | 类 | 实现/依赖 | 做了什么 |
|------|-----|----------|---------|
| {path} | {Name} | implements {X}, 依赖 {Y} | 一句话说明组装逻辑 |
```

- 只列最主要的实现类（通常 1~3 个）。
- "做了什么"关注组装逻辑而非细节：比如"拿着 provider name 从显式映射表找到 ChatModel，转成 Spring AI 格式调 LLM，落审计"。

#### ★★ 配置 / 注解（"怎么装进系统的"）

```
#### ★★ 配置 / 注解

| 文件 | 类/配置块 | 作用 |
|------|----------|------|
| {path} | {Name} | 一句话：怎么让 Spring 识别并装配 |
```

- 列出 `@Configuration` 类、`application.yaml` 关键配置块。

#### (B) 数据流向图

```
### 数据流向图

\`\`\`mermaid
graph TD
    A["调用方<br/>{入参类型}"] -->|"{方法签名}"| B["{类名}<br/>做了什么"]
    B -->|"{返回类型}"| C["{下一个类}<br/>做了什么"]
    ...
\`\`\`
```

要求：
- 从调用方出发，到最终返回，每一步标明类名 + 方法。
- **箭头上标注进出参类型**。格式：`-->|"chat(sessionId, profile, prompt) → LlmResponse"|`
- 每个节点内写一句话说明该步骤做了什么。
- 只画本课的链路；如果本课调用了前序课的接口，在节点上标注 `[L{N}]`（如 `[L16]`）。

#### (C) 配置控制点

```
### 配置控制点

> 回答：如果要换掉/改动这个模块的行为，改哪里？怎么生效？

| 控制点 | 位置 | 改法 | 生效方式 |
|--------|------|------|---------|
| {控制点名称} | {文件:行} | {怎么改} | {重启/热加载/改完即生效} |
```

- 每个控制点回答"改哪里""怎么改""改完怎么生效"三个问题。
- 通常 2~4 个控制点。

---

### 2.3 选读区——故障注入挑战

```
## 选读区

### 故障注入挑战

> 正常路径你看十遍不如故障路径走一遍。

| # | 挑战 | 改什么 | 怎么改 | 你看到什么 | 你学到什么 |
|---|------|--------|--------|-----------|-----------|
| 1 | {挑战名} | {具体位置：文件 + 类/配置项} | {具体操作步骤} | {正常现象 vs 故障现象} | {这条故障揭示的架构原理/边界} |
```

要求：
- 至少 3 条，至多 5 条。
- 每条必须**有意义**——不是随便改个变量名，而是改动后能揭示系统的架构约束、错误传播路径、配置与运行时的边界。
- "你学到什么"是核心：要讲清楚这条故障让你理解了系统的哪个设计决策或边界条件。
- 故障类型要有变化，覆盖：**配置层**（改配置看启动/运行时差异）、**注入层**（破坏 Bean 依赖看 Spring 报错）、**数据层**（传入畸形数据看异常处理链路）、**边界层**（触发上限/下限看系统兜底）。

### 2.4 费曼理解

**不是留空白——AI 直接写出来。**

用"讲给没学过的人听"的口吻，纯白话，不出现代码块、不套表格。

必须覆盖以下 6 层内容（按顺序组织）：

1. **为什么有这个模块**——它解决什么问题，不放这一层会怎样。
2. **接口和数据载体怎么拆的**——核心接口定了什么契约，数据 record 各自装什么，异常信号在什么时机抛出。
3. **一次调用的完整执行路径**——从调用方入口，经过哪些步骤（查映射→翻译工具→调 LLM→提取响应→写审计），到最后返回出参，每一步传什么返什么。
4. **关键设计决策和为什么**——挑本节最重要的 2~4 个设计点，各用一两句话解释原因（如：为什么不靠类型扫描、为什么关自动执行、为什么审计是旁路）。
5. **故障注入实验揭示的边界**——从故障注入挑战中挑 2~3 条最关键的，用"如果…就会…，所以…"的句式融入叙述，不是列表面。
6. **模块分层**——一句话收尾：这些类分属哪几个 Maven 模块，每层管什么。

格式模板：

```markdown
### 费曼理解

{纯白话叙述，约 200 字以上，无代码无表格}
```

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 给 Agent 配上"到点自己说话"的能力 (Priority: P1)

运营者想部署一个"每天早上 9 点推送天气播报"的 Agent。他只需要在 Agent 的描述文件里声明一条定时规则（什么时间触发、在哪个时区、到点说什么话），重启系统后就不用再管——到点系统自动拼一条消息发起一次对话，Agent 照常思考、调工具、往外推消息，整个过程跟人手动发消息没有区别，审计账照记。

**Why this priority**: 这是本模块存在的全部理由——"钟推"。配置驱动（改时间不用改代码）是"配置即 Agent"原则的延伸，是本模块的地基。

**Independent Test**: 给某 Agent 声明一条"每分钟触发"的定时规则，重启系统，到点观察 Agent 自动发起对话，且 LLM 调用、工具调用都有审计记录；改触发时间（如改为每 5 分钟）不重新编译、重启后按新时间跑。

**Acceptance Scenarios**:

1. **Given** Agent 描述文件中声明了一条定时规则（cron 表达式 + 时区 + 消息内容），**When** 系统启动，**Then** 该规则被注册进调度器，触发参数（时间表达式和时区）与声明完全一致
2. **Given** 规则声明的时区是显式的（如 Asia/Shanghai），**When** 系统注册该规则，**Then** 触发时间按时区计算，不由服务器系统时区代替
3. **Given** 定时规则触发，**When** 一次触发完成，**Then** 对话过程走与 CLI/Web 完全相同的处理链路，LLM 调用与工具调用审计照记
4. **Given** 定时规则触发，**When** 会话建立，**Then** 会话身份固定为（scheduler, scheduler, 该 Agent 名），同一个 Agent 的历次定时触发复用同一个会话

---

### User Story 2 - 上次没跑完，这次就不重跑 (Priority: P2)

某定时任务一次执行要跑很久（比如 ReAct 循环反复调工具），如果跑的时间超过了触发间隔，下一次触发点到了不能又起一份——同一个任务同一时刻只能有一份在执行。到点了发现上一份还在跑，直接跳过本次触发，不排队、不堆积。

**Why this priority**: 防止同一任务并发跑两份造成重复副作用（重复推送、重复记账），是定时任务正确性的底线。

**Independent Test**: 构造"上一次触发还在执行中"的状态，再触发一次，断言第二次触发被跳过、没有发起新的对话处理。

**Acceptance Scenarios**:

1. **Given** 某个定时任务上一次触发尚未结束（锁被占用），**When** 下一次触发点到达，**Then** 本次触发直接跳过，不发起新的对话处理，也不排队等待

---

### User Story 3 - 一次失败不拖垮全局 (Priority: P3)

某次定时任务执行过程中出了异常（模型调用失败、工具抛错等），调度器本身不能崩——其他定时任务照常触发，本次失败在日志里留痕，锁必须释放，下一次触发点还能正常进来。

**Why this priority**: "失败不崩、留痕可查"是核心阶段对失败处理的要求；锁不释放会让任务永久卡死，是最隐蔽的故障形态。

**Acceptance Scenarios**:

1. **Given** 某次触发处理过程抛出异常，**When** 异常发生，**Then** 异常不外抛、仅记日志，调度器继续运行
2. **Given** 上述异常发生后，**When** 下一次触发点到达，**Then** 触发能正常进入处理（锁已在释放状态），再次发起对话处理——证明没有永久卡死

---

### Edge Cases

- 时区未显式声明时怎么办：按系统默认时区处理（配置允许显式声明，未声明回退系统时区）
- cron 表达式非法：注册时报错记录，不影响其他合法任务注册
- 同一个 Agent 声明多条定时规则：每条规则独立注册、独立拿锁
- 两个 Agent 声明了相同的任务 id：属配置错误（全局唯一是操作者责任），系统核心阶段不强制校验——防重叠锁按 id 键，重名会导致两任务共用一把锁，第 28 节落库时主键冲突会显式报错
- 任务定义只有声明没有实际 Agent：不阻断系统启动

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持在 Agent 配置中声明一条或多条定时规则，每条规则含：任务标识（全局唯一，操作者责任）、触发时间表达式、时区、到点要说的话
- **FR-002**: 系统 MUST 在启动时扫描所有 Agent 的定时规则并全部注册进调度器；触发规则完全来自配置，改规则不需要改代码
- **FR-003**: 系统 MUST 在注册时同时使用规则声明的触发时间表达式和时区（不用服务器系统时区替用户做主）；时区未声明时回退系统时区
- **FR-004**: 系统 MUST 保证同一时刻同一任务最多一份在执行：上一次未结束而触发点到达时，本次触发直接跳过、不排队、不堆积
- **FR-005**: 系统 MUST 在一次触发内部发生异常时：异常不外抛、仅记日志留痕、释放该任务的占用——调度器不崩、其他任务不受影响、下一次触发还能正常进入
- **FR-006**: 系统 MUST 为定时触发的会话固定使用身份（scheduler, scheduler, Agent 名），同一个 Agent 的历次定时触发复用同一会话，会话历史自然累积并按既有规则截断
- **FR-007**: 定时触发的对话 MUST 走与 CLI/Web 完全相同的处理入口，审计（LLM 调用、工具调用）照常落库，不为定时触发单独开一套逻辑
- **FR-008**: 触发时任务"到点说什么话"的内容来自规则声明，由 Agent 配置决定，系统不预置任何具体话术

### Key Entities *(include if feature involves data)*

- **定时规则（Schedule）**: 一次定时触发的完整声明：任务标识（全局唯一，跨 Agent 不重名，操作者责任）、触发时间表达式、时区、到点消息内容；依附于某个 Agent 的配置，随进程启动注册
- **调度任务（Scheduled Task）**: 运行期由"规则 + Agent"实例化出的可触发单元，进程内执行、靠任务级锁防重叠；状态与执行历史不落库（第 28 节补齐）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 运营者新增/修改一条定时规则（改时间、改话术、增删规则）不需要改代码，重启后按新规则运行
- **SC-002**: 同一任务在重叠触发场景下（执行时间长于触发间隔）始终最多一份在执行，零并发执行
- **SC-003**: 任一次定时触发失败（任意异常），调度器继续运行、其他任务照常触发、该任务下一次触发照常进入，零永久卡死
- **SC-004**: 定时触发的每次对话在审计账上完整可查（LLM 调用、工具调用），与人工触发的对话无记账差异

## Assumptions

- 核心阶段单实例部署，防重叠用进程内机制即可，不做分布式协调（选主/分布式锁/租约）——扩展阶段
- 任务失败后不自动重试、不自动告警，做到"失败不崩、留痕可查"——扩展阶段
- 任务状态与执行历史不落库、无管理接口（查看/立即执行/启用停用）——第 28 节补齐
- 任务定义只能写在 Agent 描述文件里、随进程启动注册，运行时增删任务——扩展阶段
- 调度能力复用平台自带能力（Spring TaskScheduler），不自己造调度器
- 前序交付依赖：Agent 配置与注册（第 16 节）、统一处理入口与审计（第 17 节）、会话三元组管理（第 18 节）

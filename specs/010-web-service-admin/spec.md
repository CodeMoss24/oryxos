## User Scenarios & Testing *(mandatory)*

### User Story 1 - 业务系统与 Agent 连续对话 (Priority: P1)

业务系统要跟 Agent 保持连续对话：先创建会话拿到会话标识，之后多次向该会话发消息，随时查会话历史，用完归档。发消息走的是与 CLI 完全相同的处理链路——同一个引擎、同样的审计记录，Controller 只是薄壳（参数校验、响应包装、错误处理），不夹带任何业务逻辑。

**Why this priority**: 会话管理是业务系统最常用的接入路径，也是"Web 与 CLI 共享引擎"这条架构底线的第一个验证点。

**Independent Test**: 创建会话 → 发消息（正常处理）→ 查历史（能看到刚才的消息与回复）→ 归档。可只测会话层而无需真模型（处理引擎可替换为替身验证"恰被调用一次"）。

**Acceptance Scenarios**:

1. **Given** 业务系统发起创建会话请求，**When** 请求合法，**Then** 返回新会话标识与状态，该会话可被后续消息请求引用
2. **Given** 会话存在且消息合法，**When** 业务系统向该会话发消息，**Then** 回复由与 CLI 相同的处理引擎产出，处理引擎恰被调用一次（Controller 无夹带逻辑）
3. **Given** 会话存在，**When** 业务系统查询会话历史，**Then** 返回该会话的最近对话记录，最多 100 条
4. **Given** 会话存在，**When** 业务系统归档该会话，**Then** 会话转为归档状态，不再参与新对话
5. **Given** 消息为空或超过 32KB，**When** 业务系统发消息，**Then** 返回 400 参数错误，处理引擎不被调用
6. **Given** 会话标识不存在，**When** 业务系统发消息或查历史，**Then** 返回 404 资源不存在

---

### User Story 2 - 业务系统一次性调用 Agent (Priority: P1)

业务系统不想管理会话，只想把一句话丢给某个 Agent、拿回结果就走。调用最长 60 秒：正常时限内返回结果；超过 60 秒直接终止返回超时错误，不无限挂起。

**Why this priority**: 无状态调用是业务系统最轻量的接入方式（告警分析、审批辅助等短任务），与"连续对话"构成两条互补的主路径。

**Independent Test**: 按 Agent 名发起调用请求（处理引擎以替身替代），断言结果正常返回、引擎恰被调用一次；构造超 60 秒的场景断言返回超时错误。

**Acceptance Scenarios**:

1. **Given** Agent 名存在，**When** 业务系统发起无状态调用，**Then** 返回该 Agent 的回复，调用过程与 CLI 对话走同一处理引擎
2. **Given** 调用处理在 60 秒内完成，**When** 请求返回，**Then** 返回正常结果
3. **Given** 调用处理超过 60 秒，**When** 超时发生，**Then** 返回 504 超时错误，请求被终止
4. **Given** Agent 名不存在，**When** 业务系统发起调用，**Then** 返回 404 资源不存在

---

### User Story 3 - 查询 Profile / Tool / 长期记忆 (Priority: P2)

运维或业务方想了解底座里有什么：当前有哪些 Agent 描述（Profile）、注册了哪些工具、长期记忆里记了什么。三个只读查询端点各给一个列表或全文，不提供任何修改能力。

**Why this priority**: 查询能力让外部系统能"看见"底座状态，是管理平台的数据来源，也是运维排障的基本盘。

**Independent Test**: 注册若干 Profile 与工具、写入长期记忆后，分别请求三个查询端点，断言返回内容与实际注册/存储一致；端点不存在写入口。

**Acceptance Scenarios**:

1. **Given** 系统中注册了若干 Profile，**When** 请求 Profile 列表，**Then** 返回全部 Profile 的概要信息
2. **Given** 系统中注册了若干工具，**When** 请求工具列表，**Then** 返回全部可用工具的名称与描述
3. **Given** 长期记忆存在内容，**When** 请求长期记忆，**Then** 返回记忆完整数据（全文，不做注入视图的归档截断）
4. **Given** 上述任一请求，**When** 请求发起，**Then** 不存在任何创建/修改/删除入口

---

### User Story 4 - 系统状态与健康检查 (Priority: P2)

外部系统或部署脚本想知道底座活着没有：健康检查返回"活着"；运行信息端点在此基础上多带一份各模型 Provider 的连通状态，便于定位"是底座挂了还是 Provider 挂了"。

**Why this priority**: 健康检查是接入方与部署脚本的第一依赖（负载均衡探活、部署验收都靠它）；Provider 连通状态让排障少一步猜测。

**Independent Test**: 请求健康检查断言返回 ok；请求运行信息断言包含各 Provider 的连通状态字段。两者均不依赖真实模型即可返回。

**Acceptance Scenarios**:

1. **Given** 服务在运行，**When** 请求健康检查，**Then** 返回 ok 状态
2. **Given** 服务在运行，**When** 请求运行信息，**Then** 返回版本等运行信息与各 Provider 的实时连通状态（真实探测：连通/断开，探测超时或失败按"断开"返回，不拖垮端点本身）

---

### User Story 5 - 第一版只读管理平台 (Priority: P3)

运维打开浏览器访问管理台地址，左侧五项导航（会话列表、Profile 列表、Tool 列表、长期记忆、运行状态），右侧把五个查询端点的数据渲染成表格或文本。整个界面没有任何新建/编辑/删除按钮；请求出错时把统一错误信封里的 message 展示出来，不白屏；空数据、加载中、错误三种状态都有明确占位。刷新子路径不 404。

**Why this priority**: 管理平台没有自己的后端、全靠 10 个端点——它的可用性同时验证了"API 是完备的对外通道"这件事本身，是本节第二个交付物。

**Independent Test**: 起服务后浏览器访问管理台地址，五页均能渲染真实数据（先造好会话/Profile/工具/记忆/状态数据），逐页检查无任何写操作入口；构造一个出错场景断言页面显示错误 message 而非白屏。

**Acceptance Scenarios**:

1. **Given** 底座内有会话数据，**When** 打开会话列表页，**Then** 会话以表格渲染
2. **Given** 底座内有 Profile/Tool/记忆/状态数据，**When** 分别打开对应页面，**Then** 各页渲染对应数据
3. **Given** 管理台任意页面，**When** 浏览界面，**Then** 不存在新建/编辑/删除任何资源的入口
4. **Given** 某查询请求失败，**When** 页面收到统一错误信封，**Then** 页面显示信封中的 message，不白屏
5. **Given** 页面数据为空或加载中，**When** 浏览界面，**Then** 显示明确的空态/加载态占位
6. **Given** 用户在管理台子路径刷新浏览器，**When** 刷新发生，**Then** 仍能回到管理台页面（不 404）

---

### Edge Cases

- 消息长度恰好 32KB 边界怎么判？（等于 32KB 视为合法，超过才拒绝）
- 会话历史超过 100 条时返回哪 100 条？（最近的 100 条）
- 内部异常（数据库连接失败等）发生时会向外部泄漏什么？（只给统一话术"内部错误"，细节进日志）
- Provider 探活本身失败时运行信息端点是否可用？（可用，返回"断开"状态而非报错）
- 管理台静态资源路径与 API 路径冲突时怎么处理？（管理台子路径请求未命中静态文件时回落首页，API 路径不受影响）

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供 11 个 REST 端点，统一前缀 `/api/v1`：创建会话、发消息、查会话历史、归档会话、会话列表（只读扩展，供管理台"会话列表"页）、按名调用 Agent、列 Profile、查长期记忆、列工具、健康检查、运行信息
- **FR-002**: 发消息与按名调用两个入口 MUST 与 CLI 共享同一个处理引擎；Controller 只做参数校验、响应包装、错误处理，正常请求下处理引擎恰被调用一次
- **FR-003**: 所有端点 MUST 使用统一响应信封（`code`、`message`、`data`、`timestamp`），成功与错误共用
- **FR-004**: 所有异常 MUST 统一转成标准错误响应，各端点不得自行拼接错误体；错误码约定：400 参数错误、404 资源不存在、500 内部错误、503 Provider 故障、504 调用超时
- **FR-005**: 500 兜底响应 MUST 只给统一话术"内部错误"，内部异常细节（连接串、堆栈等）只进日志，一个字不得出现在响应体
- **FR-006**: 单条消息 MUST 限制最大 32KB，超限返回 400
- **FR-007**: 会话历史 MUST 最多返回最近 100 条
- **FR-008**: Agent 调用 MUST 有最长 60 秒上限，超时返回 504
- **FR-009**: 常驻服务 MUST 默认监听 8080 端口，请求运行在虚拟线程上（不引入响应式编程模型）
- **FR-010**: 常驻服务 MUST 只凭一个 Provider 的环境变量密钥即可启动成功；Spring AI 的 eager 模型自动装配被显式排除，不向启动方索要额外密钥
- **FR-011**: 核心阶段 CORS MUST 开放所有源（方便调试），扩展阶段再加白名单
- **FR-012**: OpenAPI 文档 MUST 自动生成并暴露在 `/swagger-ui`
- **FR-013**: 管理平台 MUST 为只读单页应用，左侧五项导航（会话列表、Profile 列表、Tool 列表、长期记忆、运行状态），分别调 `GET /api/v1/sessions`（只读列表扩展）、`GET /api/v1/profiles`、`GET /api/v1/tools`、`GET /api/v1/memory`、`GET /api/v1/info` 渲染
- **FR-014**: 管理平台 MUST 无任何新建/编辑/删除入口；接口失败时显示统一错误信封中的 message；空/加载/错误三态均有明确占位
- **FR-015**: 管理平台 MUST 托管在 `/admin` 子路径，构建产物使用相对资源路径；SPA 子路径刷新 MUST 回落到管理台首页而非 404，`/api/v1` 路径不受回落影响
- **FR-016**: 管理平台视觉风格 MUST 钉死到项目官网首页的设计 token（深色 + 橙主色、指定字体、左导航布局、克制圆角），不引外部 UI 技能；这套 token 与工程约定 MUST 沉淀为项目内技能文件，供后续加页面复用
- **FR-017**: 运行信息端点 MUST 返回各 Provider 的实时连通状态：对 Provider 地址做带超时的轻量探测，成功标"连通"，超时/失败/未配置标"断开"；探测本身失败不得导致运行信息端点报错
- **FR-018**: 长期记忆端点 MUST 返回记忆完整数据（全文），不得使用注入视图的归档截断；实现方式为 Memory 门面与存储接口增量新增只读方法 `readAll()`，三档后端各自原样读取、均不截断；既有注入视图方法（`buildContext`）与其截断策略保持不动

### Key Entities

- **会话（Session）**: 前序节已交付——唯一标识按"渠道 + 用户 + Profile"拼接，持久化存储，含消息历史；本节仅通过端点读写，不改变其结构
- **错误信封（Error Envelope）**: 统一错误响应体，含错误码、面向外部的 message、时间戳；内部异常细节不出信封
- **Agent 调用**: 一次性请求——Agent 名 + 消息内容进，回复出；无会话持久化

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 10 个端点全部可用，curl 真链路（含真模型发消息）逐条走通，审计有账
- **SC-002**: 自动化验收测试全绿：超 32KB → 400、会话不存在 → 404、正常请求处理引擎恰被调用一次、每类异常映射到约定状态码、500 响应不含内部异常细节
- **SC-003**: 常驻服务在只配置一个 Provider 密钥的干净环境下启动成功，管理台五页渲染真实数据、无写操作入口
- **SC-004**: CLI 聊过的会话能从 Web 会话历史查到（两个入口共享存储）
- **SC-005**: 200 并发调用下服务稳定不退化（虚拟线程生效）
- **SC-006**: `/swagger-ui` 接口文档齐全，覆盖全部 10 个端点

## Assumptions

- 前序节已交付处理引擎、会话层（持久化 + 标识拼接规则）、Profile 注册表、Tool 注册表、Memory 门面、Provider 层——本节只做包装，不重造
- 错误映射口径按课件草图（并经用户确认）：Session/资源不存在类异常 → 404，Provider 故障类异常 → 503（既有映射迁改），参数错误 → 400，超时 → 504；500 兜底不泄漏内部细节
- Provider 连通探活扩展核心层 Provider 端口（16 节公共接口的增量扩展，经用户确认），新增方法只做探活、不改既有 chat 契约
- Memory 全文读取经 Memory 门面与存储接口增量新增 `readAll()`（22 节公共接口的增量扩展，经用户确认），注入视图截断策略保留不动
- 本节收尾需同步的文档措辞（经用户确认）：① 宪法/TS §7.2/CLAUDE.md 的"10 个端点"改为"核心阶段 10 个端点（会话列表为只读扩展）"类表述；② TS §7.2/CLAUDE.md 的"查长期记忆（MEMORY.md）"泛化为"长期记忆全文"
- CORS 全开遵循 TechnicalSolution §7.4 的权威约定（课件未提及但不冲突）
- 管理平台与官网首页同技术栈与视觉 token；前端构建需 node/npm 工具链
- 认证（假设内网部署）、SSE、WebSocket、RBAC、限流、通过 API 定义 Agent（含 Profile 增删改、Memory 写入、Webhook 触发、Prometheus metrics）均不在本节范围

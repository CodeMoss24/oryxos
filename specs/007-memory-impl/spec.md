# Feature Specification: Memory 长期记忆实现

**Feature Branch**: `022-lesson22-memory-impl`

**Created**: 2026-08-11

**Status**: Draft

**Input**: User description: "第22节需求：Memory 实现——MemoryService 统一门面 + 可插拔的长期记忆后端接口，核心阶段一次交付三档后端，靠配置切换、上层一行不改"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Agent 记住用户偏好并在后续对话自动带上 (Priority: P1)

用户在对话中透露偏好（如"用户叫小王，偏好用 Java"），Agent 判断值得长期记住，主动调用记忆保存能力写入长期记忆。下一轮及以后每一轮对话组装上下文时，这条记忆自动出现在系统提示里，用户不需要重复说明。

**Why this priority**: 这是 Memory 能力存在的根本价值——"记得住"让 Agent 从无状态工具变成有成长记录的助手。写入后立即可见（无缓存）是该故事的验收底线，也是三档后端共有的契约。

**Independent Test**: 写入一条记忆后立即读取上下文和检索，均能命中刚写入的内容——不依赖任何真实模型，纯本地可自动化验证。

**Acceptance Scenarios**:

1. **Given** 长期记忆为空，**When** 写入一条归档记忆"用户叫小王，偏好用 Java"，**Then** 下一次读取上下文能立即看到该条记忆（写入后立刻可读，不允许有缓存）。
2. **Given** 同一条记忆已写入归档区，**When** 按关键词检索"小王"，**Then** 检索结果命中该条记忆。
3. **Given** 写入了一条核心记忆"用户叫小王"，**When** 归档区灌入远超阈值的流水记录，**Then** 读取上下文时核心记忆一字不少地完整在场，归档区最早的内容被裁掉、保留最近的。

---

### User Story 2 - 记忆量增长时只改一行配置切换后端 (Priority: P1)

记忆量小的时候用默认的 Markdown 文件（人可读、git 可跟踪、零依赖）；记忆量上千、需要结构化查询时，把配置从 markdown 改成 sqlite，记忆按条入库、截断变 LIMIT、检索变 LIKE；真要语义检索/自动提炼时切到自托管的 Mem0 外部服务。三次切换，上层代码（对话、工具、上下文组装）一个字不改。

**Why this priority**: 这是"接口墙"价值兑现的直接证据——同一套上层代码、同一套契约测试，背后从"一个文件"平滑换到"一个外部记忆服务"。三档后端一次交付是本节核心交付物。

**Independent Test**: 同一套契约测试对三个后端实现参数化运行全部通过，即证明切换后端不破坏任何行为契约。

**Acceptance Scenarios**:

1. **Given** 配置选择任意一档后端，**When** 运行同一套契约断言（写入后立读、截断只裁归档、scope 路由、recall 只搜归档区），**Then** 三档后端全部通过，任何一档破契约立刻变红。
2. **Given** 后端为 Markdown 档，**When** 记忆量超过归档阈值，**Then** 读取上下文时归档区按字符串截断保留最近内容，核心区不受影响。
3. **Given** 后端为 SQLite 档，**When** 归档区记录超过上限条数，**Then** 读取上下文时只保留最近 N 条归档记录，核心区记录全量在。
4. **Given** 后端为 Mem0 档（外部服务），**When** 调用写入与检索，**Then** 请求发往自托管服务且 scope 随请求体携带，检索走语义能力。

---

### User Story 3 - Agent 显式决定记忆归核心还是归档 (Priority: P2)

Agent 调用记忆保存时显式指定 scope（core 或 archival，缺省 archival），系统不猜测该记到哪。核心记忆"始终在场"、完整注入每次上下文；归档记忆允许截断和检索。用户可以让 Agent 把长期身份特征记进核心区、把流水类信息记进归档区。

**Why this priority**: scope 显式指定是"系统不猜"契约的体现，也是核心/归档分区机制能成立的前提。优先级 P2 因为它在故事 1 的链路内，但与故事 1 可独立验证。

**Independent Test**: 分别用 core 与 archival 写入内容，验证各自落到正确分区；检索只命中归档区，核心区内容永远完整可见。

**Acceptance Scenarios**:

1. **Given** 用户调用保存并指定 scope=core，**When** 读取上下文，**Then** 内容出现在核心区且永不参与截断。
2. **Given** 用户调用保存且未指定 scope，**When** 读取上下文，**Then** 内容缺省写入归档区。
3. **Given** 核心区存在记忆"用户叫小王"，**When** 按关键词检索"小王"，**Then** 检索结果**不**包含核心区内容（核心区全量在场不需要检索），归档区内的匹配内容正常返回。

---

### User Story 4 - Agent 通过工具读写长期记忆,未命中不报错 (Priority: P2)

Agent 在对话中调用保存记忆和检索记忆两个内置工具完成读写；检索无命中时工具返回友好提示（"没有找到相关记忆"）而不是抛异常打断对话。工具对底层后端无感知——换后端不影响工具行为。

**Why this priority**: 这是 Memory 能力对 Agent（而非仅对 PromptBuilder）的暴露面，是 Demo 二"日报体现用户偏好"的调用入口。优先级 P2 因为依赖前三个故事的底层能力。

**Independent Test**: 调用工具写入一条记忆、检索命中；检索不存在的内容返回友好提示。

**Acceptance Scenarios**:

1. **Given** 对话上下文，**When** Agent 调用保存工具且未带 scope，**Then** 记忆缺省写入归档区，返回成功确认。
2. **Given** 归档区没有"航天"相关内容，**When** Agent 调用检索工具查询"航天"，**Then** 返回"没有找到相关记忆"，不抛异常。
3. **Given** 归档区有"偏好 Java"，**When** Agent 调用检索工具查询"Java"，**Then** 返回命中内容。

---

### Edge Cases

- 记忆文件不存在（首次使用）时读取与写入都不抛异常，能正常初始化并写入。
- 归档区为空时检索返回空结果而非异常。
- 检索关键词为空或纯空白时不抛异常（返回无命中提示或空结果）。
- 保存时 scope 值不规范（非 core/archival）时按缺省处理写归档，不抛异常。
- 并发写入同一记忆文件时不产生内容丢失或文件损坏（写入操作互斥）。
- 记忆内容本身包含分区 header 字样时不影响分区解析正确性（按 header 定位插入点与截断边界）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供统一的记忆门面对上层暴露三个固定方法——给上下文组装用的"读取长期记忆"，给工具用的"记一条"和"查一下"。上层只认门面，不感知底层后端。
- **FR-002**: 系统 MUST 提供可插拔的长期记忆后端接口，接口定义写入（含分区）、读取、关键词检索三个操作；接口签名不得携带任何存储实现细节（不出现"文件""表""白名单"等字样）。
- **FR-003**: 系统 MUST 提供三档后端实现，默认档为 Markdown 文件（一个分区文件、两个区块），SQLite 档（记忆按条入库）与 Mem0 档（自托管外部服务）为递进升级档。
- **FR-004**: 系统 MUST 通过一个配置项（取值 markdown/sqlite/mem0）决定装配哪档后端，默认 markdown；换后端只改这一行配置，门面以上代码零改动。
- **FR-005**: 三档后端 MUST 共同遵守四条行为契约：①不缓存——每次读取都重新读文件/查库/调服务，写入后下一轮立刻可见；②核心记忆永不被截断，截断只作用归档区；③写核心还是写归档由调用方经 scope 显式指定（core/archival，缺省 archival），系统不猜；④关键词检索不做复杂化（行包含匹配 / LIKE / 服务自带检索）。
- **FR-006**: 系统 MUST 提供两套契约测试对三档后端参数化统一运行——任何一档违反契约测试立即失败。
- **FR-007**: 系统 MUST 提供两个内置记忆工具给 Agent：保存（content + 可选 scope，缺省写归档）与检索（keyword，未命中返回友好提示不抛异常）；工具对底层后端无感知，三档后端共用。
- **FR-008**: 系统 MUST 在每次组装系统提示时把长期记忆（核心区全量 + 归档区截断后）注入；会话历史段由上层独立负责，两者一起注入、不重复。
- **FR-009**: 外部集成档（Mem0）的地址与凭证 MUST 走环境变量占位，不落明文配置。
- **FR-010**: SQLite 档的数据表 MUST 以手工建表脚本方式创建（与审计表同口径），不依赖自动建表；实体与仓库落在既有持久化模块的统一扫描包内。
- **FR-011**: 现有早期雏形接口签名（会话历史与长期记忆合并返回、scope 用字符串、检索返回单串）MUST 按第 21 节评审定死的签名对齐：门面三方法语义为"读取长期记忆上下文 / 记一条 / 查一下返回列表"，现有调用方同步适配；会话历史段职责移交上层组装，避免重复注入。

### Key Entities

- **长期记忆分区（scope）**: 核心（CORE）与归档（ARCHIVAL）两类。核心记忆全量注入每次上下文、永不截断、不参与检索；归档记忆可截断、可检索。
- **记忆条目**: 一条长期记忆内容，含所属分区与写入时间。Markdown 档以带日期的列表行形式存在；SQLite 档以数据行存在；Mem0 档以消息+元数据形式存在。
- **后端实现**: 三档可互换的存储形态（文件 / 数据表 / 外部服务），对上层仅通过后端接口可见。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一套契约断言（写入后立读、截断只裁归档核心一字不少、scope 路由、检索只搜归档区）对三档后端参数化运行全部通过，任何一档破契约立即失败——"接口不变、实现随便换"有自动化保障。
- **SC-002**: 写入一条记忆后，不经过任何缓存等待，下一次读取上下文立即可见该条记忆。
- **SC-003**: 归档区灌入远超阈值的内容后，读取结果中核心记忆一字不少，归档区保留最近内容、最早内容被裁掉。
- **SC-004**: 检索未命中返回友好提示、不抛异常；scope 缺省写归档、不规范取值按归档处理。
- **SC-005**: 换后端仅需修改一行配置，门面以上代码与测试零改动。
- **SC-006**: 人工验证：同一段对话分别用 markdown 与 sqlite 后端跑通（写入→下一轮上下文带上），体感一致；真模型对话中 Agent 主动调保存、开新会话后核心记忆仍在场。

## Assumptions

- 前序节已交付并可用：会话模型与会话管理（会话历史独立负责注入）、上下文组装器、工具注册体系、SQLite 手工建表口径。
- 持久化模块的实体/仓库扫描包范围固定，本节新增的记忆条目实体与仓库必须落入该扫描范围才能被装配。
- 现有记忆模块为早期雏形（含未解析参数的保存工具、无截断的 Markdown 实现、无 SQLite/Mem0 两档、无任何测试），本节按定死签名重写补齐，属本节交付物范畴而非修改前序节正式交付物。
- 记忆模块新增对本项目持久化模块的依赖（复用既有 SQLite/JPA 能力）与 Spring Web 依赖（外部服务集成用），均为项目既有技术栈内的依赖。
- Mem0 外部服务为可选人工验证项，自动化测试用内存替身模拟其行为，不依赖真实服务。
- 记忆量阈值与截断策略采用课件给定值（归档区字符上限 / 归档区条数上限），为简单截断，不做压缩。
